SWP Sandbox: A local Figma-like sandbox between Cursor and the deployed site

Product Sector: Internal tooling / design workflow
Team: Me
Duration: Built alongside the Second Wind Pro redesign
Tools: Cursor
Status: Local, in active use for SWP work
OVERVIEW

SWP Sandbox is an internal tool I built to sit between Cursor and the live Second Wind Pro site. It started as a workflow fix during the website redesign, then became its own project: a local library for drafts, frozen versions, and a canvas that lets me preview and mark up the site across breakpoints without redeploying.

CHALLENGE

Every design check meant a round trip through GitHub and Netlify.

Redesigning the Second Wind Pro website surfaced a second problem I didn't expect to be solving: my own workflow. Every time I wanted to check whether a particular design element held up (athlete cards on mobile, services carousel on iPad), I had to commit to GitHub, deploy to Netlify, and go look. That loop was fine for one check. It was not fine for the number of times I needed to make it.

INSIGHT

I didn't need a better deployment pipeline. I needed a middleman.

I'd talked to John IntraterJohn Intrater, a Product Designer at Faire, about a similar problem. He'd built an internal playground tool for himself and his coworkers. That conversation stuck with me. Something local, fast, and mine that sat between Cursor and the live site would close the gap better than speeding up deploys.

THE TOOL

A Figma / Google Docs–style library for site versions

SWP Sandbox lets me:

  • Create, rename, and duplicate draft files pulled straight from the Cursor project, without touching GitHub or Netlify
  • Preview any draft across breakpoints (mobile, iPad, desktop) in one place
  • Keep a working history of drafts, so I can show progress as a sequence rather than a single “current version”
  • Freeze a working copy into a version, and set a frozen version as live on Netlify when it's ready

The homepage is a file library: Playground (the working copy), drafts, and frozen versions, each with a status (working, live, or frozen) and a homepage preview. Hovering a card opens Canvas or Open, depending on whether I need to mark something up or just look at it in the browser.

THE CANVAS

Preview, annotate, and mark design changes at real viewport sizes

Canvas is where the sandbox actually replaces the deploy loop. I open a file, pick a viewport, and work on the live preview instead of waiting for Netlify.

Three modes:

  • Browse: interact with the live site as a visitor would
  • Annotate: yellow pins, boxes, and sketches for feedback
  • Design: cyan marks for intended design changes

The left rail holds the viewports I actually design against: Desktop XL 1440×900, Desktop 1280×832, Breakpoint 980×800, Tablet 768×1024, Mobile 390×844, and Mobile SM. Marks save per viewport, so a mobile note stays on mobile. The preview iframe uses the real pixel width, so CSS media queries kick in correctly instead of scaling a desktop layout down.

From the canvas I can copy notes into Cursor, or open the folder in Cursor and keep going. The point is to stay in the loop between looking and making, without a deploy in the middle.

RESULT
